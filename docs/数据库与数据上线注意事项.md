状态以 2026-11-01 为准；表中"已核实"指已对照代码或实际运行结果，"待核实"指尚未验证。

## 2. 把现有数据库带上线

1. **数据库不随代码走**：`server/data/` 在 `.gitignore` 中，提交代码不会包含数据库，必须单独搬运。
2. **不要直接拷贝 `ssq.db` 单个文件**：库是 WAL 模式，最新写入可能还在 `ssq.db-wal` 里。可选做法：
   - 使用 SQLite 备份接口（better-sqlite3 的 `database.backup()`，补数脚本用的就是这个）；
   - 或 `VACUUM INTO '目标文件'`；
   - 或停止所有进程后，把 `ssq.db`、`ssq.db-wal`、`ssq.db-shm` 一起处理。
3. **不要依赖“先删 `.gitignore`，上线后再加回来”**：这个做法不可靠。`gitignore` 只对未跟踪文件生效；一旦数据库已提交，后续再加回 `.gitignore` 也不会自动从历史中移除。最后只能 `git rm --cached`，并且需要强制推送，风险很大，容易把生产库和代码历史混在一起。
4. **更稳妥的操作步骤**：
   - 在本地服务器/开发机上，确保所有进程已停掉，避免数据库处于写入状态；
   - 用 SQLite 备份接口或 `VACUUM INTO` 生成一个一致快照，输出到单独目录，如 `server/data/releases/ssq-release-<时间>.db`；
   - 只传输这个快照，不传 `node_modules`、不传 Git 变更、不传代码之外的工作树；
   - 把快照上传到目标服务器的 `server/data/` 目录，并确保 `server/data/ssq.db` 与 `ssq.db-wal` / `ssq.db-shm` 的版本一致；
   - 在目标服务器上先检查 `PRAGMA integrity_check`，再启动应用程序；
   - 生产上线前禁止任何额外写入（尤其不要在此时执行 `import:full` 或 `generateRecommendation`），否则会出现多来源写入。
5. **搬运后验证**：`PRAGMA integrity_check` 为 `ok`；`PRAGMA user_version` 为 4；`draws` 共 3521 行；`recommendations` 仍有 id=1 的记录；最新期号为 2026124（或已同步后的更新期号）。
6. **生产环境重新安装依赖**：在 Linux 上执行 `npm ci`，不要拷贝 Windows 的 `node_modules`，`better-sqlite3` 是原生模块，跨系统不可用。
7. **代码版本不得低于数据库版本**：迁移在启动时自动执行；数据库版本高于代码支持的版本时程序会拒绝启动。生产代码必须不低于本地最新代码。
8. **文件权限**：数据库目录只允许运行服务的账号读写；备份目录与数据库不放在同一块磁盘更安全。
9. **`.env` 不随代码走**：生产需单独配置 `DATABASE_FILE_PATH`、`API_HOST`（默认 127.0.0.1，由 HTTPS 反向代理对外）、`API_PORT`、`ADMIN_API_KEY`（至少 32 字符高熵随机串）。

如需更稳妥，建议把数据库和代码分开部署：代码走 Git / CI，数据库走独立备份与传输，不让它进入仓库历史。

## 4. 只能有一个写入方

- 上线后，生产库是唯一真相源。本地不要再对同一个库运行调度、同步或生成推荐。
- `UNIQUE(target_issue, strategy_name)` 只能防止同一个库内重复生成，防不了"本地一份、生产一份"两个库各自生成不同推荐，两者会形成不同的数据血统。
- 服务必须**单实例**运行（进程内同步锁只在单进程内有效）。PM2 使用 fork 模式、实例数 1，不要开 cluster。
- 本地需要继续开发时，请拷贝一份生产库的备份使用，或另建独立数据库，不要共用。
- 切换时机建议：选在一期刚开奖、下一期尚未生成推荐之后，减少与已生成推荐的冲突。

## 5. 已生成的推荐（2026125，id=1）

- 它随数据库一起带到生产，**生产环境不要重新生成**，也不要手动删除（触发器会拒绝）。
- 内容哈希 `15f09ebf081f7d4b97118d498c2363d9350b6c7512b23ceba50967b2a6095f88` 只能证明内容未被改动，**不是第三方可信时间戳**，对外不要宣称"经第三方证明生成于开奖前"。
- 如需增强可信度：在该期开奖前，把哈希发布到可公开查询的位置（例如提交到仓库或发布到公开渠道）。
- 生成截止是 20:00（保守截止，不是官方停售时刻）。

## 6. 两类数据来源的区别

- 官方数据与第三方数据混在同一张 `draws` 表，靠 `data_source` 区分，**不要删除或统一改写这个字段**。
- 增量同步只关注库内最新 100 期（见 `incrementalSyncService.ts`），不会改动 2003–2012 年的第三方数据。
- 第三方数据来自非官方、仅 HTTP 的接口：
  - 对照官方数据时，重叠的 2082 期里有 1 期不一致（2025086：官方红球 17，第三方 11）。该期在已有官方数据范围内，库内保留官方值，没有受影响；
  - 但这说明该来源并非零错误，按此比例，补入的 1439 期可能存在 0–1 期错误，且无法用官方数据核对；
  - 此处结论来自本地库对比，没有在线复核官方（官网接口曾返回 Forbidden）。
- 2003–2012 年的开奖规则与现行规则不同（如开奖日、开奖时间），历史数据可用于号码统计，但不应与现行规则下的结论混用。
- 对外展示：在小程序"关于"页或数据说明中写明"2013 年前数据来源于第三方，未经官方逐期核对"；公开接口目前不输出 `dataSource`，需要时再决定是否增加该字段。
- 计划外的"缺期提示"：2003 年最后一期为 2003089（2003-12-28），脚本按现行开奖日推算提示"可能缺少 2003090 起"。判断为早年开奖日规则不同导致的误报，**尚未核实**。

## 8. 常用核对命令（在 `server/` 目录执行）

```bash
# 来源分布与期号范围（只读）
node.exe -e "const D=require('better-sqlite3');const db=new D('data/ssq.db',{readonly:true});console.log(db.prepare('select data_source,count(*) n,min(issue) a,max(issue) b from draws group by data_source').all())"

# 结构版本与完整性
node.exe -e "const D=require('better-sqlite3');const db=new D('data/ssq.db',{readonly:true});console.log(db.pragma('user_version',{simple:true}),db.pragma('integrity_check',{simple:true}))"

npm run typecheck
npm test
```

Windows Git Bash 下 `node` 被 alias 为 `winpty node.exe`，非 TTY 时报错，请直接用 `node.exe`。
